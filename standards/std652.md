# #std652 Несоответствие индексов и условий запроса

> Область применения: управляемое приложение, мобильное приложение, обычное приложение.

*Методическая рекомендация (полезный совет)*

---

## 1. Требования к индексам

### 1.1. Условия в запросах

Для всех условий, использованных в запросе, должны существовать **подходящие индексы**.

**Секции с условиями:**
- `ВЫБРАТЬ … ИЗ … ГДЕ <условие>`
- `СОЕДИНЕНИЕ … ПО <условие>`
- `ВЫБРАТЬ … ИЗ <ВиртуальнаяТаблица>(, <условие>)`
- `ИМЕЮЩИЕ <условие>`

### 1.2. Требования к подходящему индексу

| # | Требование |
|---|------------|
| 1 | Индекс содержит **все поля** из условия |
| 2 | Эти поля находятся **в самом начале** индекса |
| 3 | Эти поля идут **подряд** (без «вклинивания» других полей) |

### 1.3. Последствия отсутствия индекса

Если подходящего индекса нет, СУБД будет **сканировать таблицу** или индекс:
- Увеличение времени выполнения
- Снижение параллельности (больше блокировок)
- Деградация производительности с ростом данных

## 2. Автоматические индексы платформы

1С:Предприятие автоматически создаёт индексы:

| Объект | Индекс |
|--------|--------|
| Справочники, документы и др. | По ссылке (уникальному идентификатору) |
| Таблицы движений регистров | По регистратору |
| Регистры накопления (остатки) | По периоду + все измерения |
| Регистры бухгалтерии (итоги) | По периоду + счёт + все измерения |

---

## 3. Дополнительное индексирование

### 3.1. Когда индексировать

Индексируйте реквизиты, когда автоматических индексов **недостаточно** и точно известен запрос, для которого индекс необходим.

**Для справочников и документов:** рекомендуется индексировать **с дополнительным упорядочиванием** — такой индекс учитывает основное представление объекта.

### 3.2. Когда НЕ индексировать

⚠️ Индексы ускоряют поиск, но **замедляют запись** (добавление, редактирование, удаление).

| Чего избегать | Причина |
|---------------|---------|
| Индексы «на всякий случай» | Лишняя нагрузка на запись |
| Первое измерение регистра | Уже есть в основном индексе итогов |
| Низкоселективные поля | Малое количество уникальных значений |
| Булево (обычно) | Только если одно значение встречается редко и всегда используется в отборе |

## 4. Примеры

Регистр накопления **ТоварыНаСкладах**:
- Измерения: Склад, Номенклатура, Качество, ХарактеристикаНоменклатуры, СерияНоменклатуры

Платформа создаст индекс: `(Период, Склад, Номенклатура, Качество, ХарактеристикаНоменклатуры, СерияНоменклатуры)`

### Запрос 1 — ❌ Неоптимальный

```1c
ВЫБРАТЬ
    ТоварыНаСкладахОстатки.Склад,
    ТоварыНаСкладахОстатки.Номенклатура
ИЗ
    РегистрНакопления.ТоварыНаСкладах.Остатки(, Номенклатура = &Номенклатура)
```

**Проблема:** Нарушено требование 2 — отбор не по первому полю индекса (Склад).

**Решения:**
- Проиндексировать измерение Номенклатура
- Переставить Номенклатуру первым измерением (осторожно!)

### Запрос 2 — ❌ Неоптимальный

```1c
ВЫБРАТЬ ...
ИЗ
    РегистрНакопления.ТоварыНаСкладах.Остатки(,
        Склад = &Склад
        И Номенклатура = &Номенклатура
        И ХарактеристикаНоменклатуры = &Характеристика)
```

**Проблема:** Нарушено требование 3 — между Номенклатура и ХарактеристикаНоменклатуры есть поле Качество, не указанное в условии.

**Решения:**
- Проиндексировать измерение ХарактеристикаНоменклатуры
- Поменять местами Качество и ХарактеристикаНоменклатуры

### Запрос 3 — ✅ Оптимальный

```1c
ВЫБРАТЬ ...
ИЗ
    РегистрНакопления.ТоварыНаСкладах.Остатки(,
        Номенклатура = &Номенклатура
        И Склад = &Склад)
```

**Требования не нарушены.** Порядок условий в запросе не обязан совпадать с порядком полей в индексе — СУБД обработает это корректно.

---

## 5. Сводка

| Правило | Описание |
|---------|----------|
| Индекс для условий | Все поля условия — в начале индекса, подряд |
| Автоиндексы | По ссылке, регистратору, периоду + измерения |
| Дополнительные индексы | Только когда известен конкретный запрос |
| Не индексировать | Первое измерение, низкоселективные поля |
