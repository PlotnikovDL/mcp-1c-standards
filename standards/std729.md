# #std729 Общие требования по разработке оптимальных запросов

> Область применения: управляемое приложение, мобильное приложение, обычное приложение.

*Методическая рекомендация (полезный совет)*

---

Прежде чем перейти к продвинутым методам оптимизации, убедитесь, что сам запрос **адекватен решаемой задаче**.

---

## 1. Минимизация объёма выборки

### 1.1. Выбирайте только нужные данные

Выбирайте **ровно те данные**, которые требуются для решения задачи.

❌ **Неправильно:**
```1c
ВЫБРАТЬ * ИЗ ...
```

✅ **Правильно:**
```1c
ВЫБРАТЬ Поле1, Поле2 ИЗ ...
```

**Принцип:** Вместо выборки большого объёма данных для последующей обработки (свёртка, сортировка, вычисления) на сервере 1С:Предприятие — спросите себя:

> «Можно ли переложить эту работу на базу данных, чтобы получить уже готовый результат?»

### 1.2. Минимизируйте количество запросов

В большинстве случаев следует минимизировать общее количество запросов к СУБД.

> См. также: #std436 — Многократное выполнение однотипных запросов

---

## 2. Не усложняйте запросы

СУБД оптимизирует и выполняет **простые запросы** более эффективно, чем сложные.

### 2.1. Рассмотрите альтернативы

| Вместо | Рассмотрите |
|--------|-------------|
| Один большой универсальный запрос | Разные (более простые) тексты запросов в зависимости от условий и параметров |
| Сложная логика в запросе | Постобработка данных на сервере 1С средствами встроенного языка |

### 2.2. Избегайте неэффективных планов выполнения

При разработке запросов **убедитесь**, что они используют эффективные планы выполнения.

⚠️ Для сложных запросов СУБД с высокой вероятностью выберет **неправильный план** — особенно актуально для **DB2**, **PostgreSQL** и **Oracle**.

**Не следует неоправданно усложнять запрос:**

| Чего избегать | Причина |
|---------------|---------|
| Вложенные запросы «для читаемости» | Усложняют план выполнения |
| Сложные условия соединения | Оптимизатор не справляется |
| Подзапросы в условии ГДЕ | Очень плохо оптимизируются |
| Конструкции ВЫБОР в условиях | Мешают использованию индексов |
| Много таблиц (>5-7) | Время анализа растёт нелинейно |

### 2.3. Проверка плана выполнения

**Инструменты:**
- Консоль запросов
- Технологический журнал
- Средства СУБД

**Признак проблемы:** `timeout warning` в плане выполнения — оптимизатору СУБД не хватило времени на поиск наилучшего плана.

---

## 3. Сводка

| Принцип | Рекомендация |
|---------|--------------|
| Объём данных | Выбирать только нужные поля и записи |
| Количество запросов | Минимизировать |
| Обработка данных | По возможности — в СУБД |
| Сложность запроса | Простые запросы лучше сложных |
| Число таблиц | Желательно не более 5-7 |
| План выполнения | Проверять на timeout warning |
