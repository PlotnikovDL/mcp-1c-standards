# #std478 Подсказка и проверка заполнения

> Область применения: управляемое приложение, мобильное приложение, обычное приложение.

---

## 1. Свойство «Подсказка»

> *Область применения (уточнение): управляемое приложение, обычное приложение.*

### 1.1. Когда задавать подсказку

Свойство **Подсказка** задаётся для объектов, которые:
- Выводятся пользователю в виде элементов интерфейса
- Требуют пояснения, расшифровки
- Требуют донесения до пользователя подробного описания назначения

**Применяется к:**
- Реквизитам объектов
- Реквизитам табличных частей
- Измерениям и ресурсам регистров

⛔ **Не добавлять** подсказки для реквизитов, используемых в ежедневной работе.

### 1.2. Содержание подсказки

⛔ В тексте подсказки **не рекомендуется:**
- Приводить инструкции
- Объяснять работу реквизита

✅ Вместо этого следует **оптимизировать сценарии работы**, связанные с реквизитом.

### 1.3. Автоматически генерируемые подсказки

⚠️ Бессмысленные подсказки, автоматически генерируемые конфигуратором при создании элементов управления (групп) на формах, нужно **очищать**.

**Примеры для удаления:**
- `Группа шапка`
- и подобные

## 2. Свойство «Проверка заполнения»

### 2.1. Обязательные к заполнению реквизиты

Для всех типизированных объектов метаданных, стандартных реквизитов и табличных частей, которые в соответствии с логикой объекта являются **обязательными к заполнению**, свойство `Проверка заполнения` должно быть установлено в **«Выдавать ошибку»**.

**Пример:** Документ `ЗаказКлиента` — запрос клиента на поставку определённого количества товара.

| Реквизит | Проверка заполнения | Обоснование |
|----------|---------------------|-------------|
| Клиент | Выдавать ошибку | Заказ без клиента не имеет смысла |
| Товары (ТЧ) | Выдавать ошибку | Заказ без товаров не имеет смысла |

### 2.2. Принцип описания ограничений в метаданных

Все ограничения и проверки должны быть (насколько возможно полно) **описаны в метаданных** конфигурации.

✅ **Правильная схема:**

```
Если хотя бы ОДИН сценарий требует обязательного заполнения:
    → Проверка заполнения = "Выдавать ошибку"
    → Исключения обрабатывать в ОбработкаПроверкиЗаполнения
```

⛔ **Неправильная схема:**

```
Проверка заполнения = "Не проверять"
+ Проверки в ОбработкаПроверкиЗаполнения
```

**Причина:** Такая схема затрудняет анализ логики работы конфигурации.

### 2.3. Условная проверка заполнения

Если проверка заполнения реквизита зависит от условий, рекомендуется управлять **автопометкой незаполненного значения** с помощью **условного оформления** форм объектов.

✅ Убирать автопометку, если при данном состоянии объекта заполнение реквизита проверять не требуется.

## 3. Сводная таблица

| Свойство | Когда использовать | Когда НЕ использовать |
|----------|-------------------|----------------------|
| **Подсказка** | Требуется пояснение назначения | Ежедневно используемые реквизиты |
| **Проверка заполнения = Выдавать ошибку** | Хотя бы один сценарий требует заполнения | Ни один сценарий не требует заполнения |
