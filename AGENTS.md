# Правила разработки mcp-1c-standards

## Назначение

- Если разработчик передал ссылку для установки, выполнить шаги из [README.md](README.md) в отдельном виртуальном окружении, зарегистрировать сервер в выбранном MCP-клиенте и проверить поиск. Для автономной установки достаточно одного клона.
- Этот репозиторий содержит Python MCP-сервер `mcp-1c-standards` для поиска по стандартам разработки 1С и сам корпус стандартов.
- Корпус находится в `corpus/standards` (перенесён из бывшего репозитория `1c-docs` с историей). Путь по умолчанию считается от каталога модуля; `ONEC_STANDARDS_DIR` остаётся переопределением.
- Не добавлять в репозиторий веса моделей, embeddings-кэш, виртуальное окружение, выгрузки синтакс-помощника и временные результаты обработки.

## Правила корпуса `corpus/`

- Стандарты хранятся в Markdown по пути `corpus/standards/std<ID>.md`. Иллюстрации находятся в `corpus/standards/assets/std<ID>/` и сохраняют расширение `.png` или `.jpg`.
- Имена файлов стандартов стабильны; не переименовывать, не удалять и массово не форматировать стандарты без отдельного согласования.
- Относительные ссылки разрешаются от каталога документа; структуру внутри `corpus/standards` не менять.
- После изменения стандартов учитывать, что сервер пересоберёт embeddings-кэш при следующем поиске. Проверка: `.md` читаются обычным текстом, затем через MCP `list_standards`, `read_standard`, при необходимости `search_standards`.

## Рабочий режим

- Перед изменением исходников или документации кратко описывать, что будет изменено и зачем, затем ждать явного подтверждения пользователя. При запросе на установку следовать разделу установки в README и сохранять существующие настройки других серверов в MCP-клиенте.
- Изменения делать маленькими шагами.
- Не менять модель, формат кэша, chunking, scoring или публичные MCP tools без отдельного согласования.
- Не коммитить изменения, не менять ветки и не выполнять операции Git с историей без прямой просьбы пользователя.

## Архитектурные границы

- Сервер отвечает только за стандарты 1С: `search_standards`, `read_standard`, `list_standards`.
- Не добавлять сюда интеграцию с `mcp-1c-ai`, BSL Language Server, EDT или синтакс-помощником.
- Автообучение, feedback-базы и пользовательская аналитика не входят в этот MCP.
- Кэш `.cache` является техническим и должен пересоздаваться из markdown-стандартов.

## Проверка

- Для изменений тестов и документации запускать из корня проверяемой рабочей копии только согласованный изолированный набор:
  ```powershell
  & .\.venv\Scripts\python.exe -I -S -B .\tests\run_isolated.py
  ```
  Для отдельной рабочей копии без своего окружения использовать абсолютный путь к согласованному интерпретатору основной копии. Набор использует установленный NumPy и синтетические документы во временном каталоге. Защита тестового процесса блокирует модели, сеть и запуск дочерних процессов. Ключи интерпретатора отключают обработку `.pth` и `sitecustomize`.
- Набор выполняет индекс с подставными моделями и проверяет контракт сервера статически через AST. Он не импортирует модуль сервера или общий runtime, не запускает MCP/WMI и не подтверждает реальный обмен `initialize` / `tools/list`.
- После изменения рабочего Python-кода дополнительно согласовать и выполнить проверку импортов индекса и сервера в изолированной среде. Импорт регистрирует инструменты MCP. При использовании соседнего runtime он также обрабатывает аргумент `--shared-worker` и создаёт прокси. Для проверки использовать изолированные каталоги и штатный скрипт `tests/check_imports.py`.
- После изменения зависимостей выполнять `python -m pip check` в согласованном изолированном окружении. Не устанавливать пакеты и не менять рабочее окружение как побочный эффект проверки.
- Если менялась логика поиска, отдельно согласовать smoke test через MCP `mcp-1c-standards` для `search_standards`, `read_standard`, `list_standards`. Внутреннее имя общего worker `1c-standards` не является именем подключения Harness и не переименовывается автоматически.
- Реальные модели, загрузки весов, пересборку рабочего кэша, WMI/HTTP-workers и подключение редакторов проверять отдельными согласованными этапами. Режим `fast` не является безмодельным.
- Ожидаемые ошибки (`expectedFailure`) фиксируют неисправленные дефекты. Код 2 изолированного набора означает такие дефекты или пропуски покрытия, а не полную успешность. Не разрешать pickle для обхода ошибки чтения NumPy-кэша. После согласованного исправления пересмотреть соответствующую отметку ожидаемого сбоя.
- В финальном ответе отдельно указывать успешные проверки, воспроизведённые дефекты, пропуски и невыполненные интеграционные этапы.
