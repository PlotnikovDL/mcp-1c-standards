# #std603 Требования к проведению документов

> Область применения: управляемое приложение, мобильное приложение, обычное приложение.

---

## 1. Назначение документов

Документы предназначены для ввода первичной информации, связанной с регистрацией событий, воздействующих на учитываемые в системе показатели.

**Примеры:**
- Финансово-хозяйственная деятельность — учёт хозяйственных операций
- Управление производством — регистрация производственных операций

---

## 2. Проведение документов

### 2.1. Общее правило

Регистрация события в системе (отражение в учёте) выполняется с помощью **проведения документа**.

✅ Большинство документов должны проводиться: свойство `Проведение` = **Разрешить**

| Состояние | Описание |
|-----------|----------|
| **Непроведённый** | «Черновик», не отражённый в учёте. Может быть не заполнен, не проверяется бизнес-логикой, не выводится в отчётах |
| **Проведённый** | «Чистовик», формирование завершено, участвует в учёте |

### 2.2. Многоэтапный жизненный цикл

Если жизненный цикл документа состоит из нескольких этапов, вводятся **дополнительные статусы**.

**Примеры:**
| Документ | Статусы |
|----------|---------|
| Заказ клиента | Не согласован → К обеспечению → Закрыт |
| Расходный кассовый ордер | Зарегистрирован в КО-3 → Подписан → Передан в кассу → Зарегистрирован в Кассовой книге |

**Правила:**
- Проведение = момент первичного отражения в учёте
- Статусы уточняют, как именно событие отражено
- При переводе между статусами — дозаполнение данных и проверки
- До проведения перевод «черновика» по статусам **не контролируется**

### 2.3. Исключения — документы БЕЗ проведения

⛔ **Не проводятся:**

1. **Документы не для учёта** — только регистрация событий с привязкой ко времени
   - Входящая корреспонденция
   - Звонки, встречи

2. **Специальные документы** с нестандартной технологией проведения
   - `Операция (бухгалтерский и налоговый учет)` — ввод операций вручную
   - `Регламентная операция` — закрытие месяца с ручной корректировкой

### 2.4. Запись с проведением

Если пользователь должен регистрировать событие и отражать в учёте **за одно действие** — записывать документ в режиме проведения.

⛔ **Недопустимо** решать эту задачу отключением проведения у документа.

---

## 3. Формирование движений

При отражении события может потребоваться формирование «вторичных» данных со сложными привязками. Такие данные помещаются в **регистры**.

### 3.1. Способы формирования движений

| Способ | Описание |
|--------|----------|
| **Автоматический** | Пользователь вводит данные в документ → при проведении генерируются движения (например, бухгалтерские проводки) |
| **Ручной** | Пользователь вводит данные непосредственно в регистры (ручные операции, начальные остатки) |

### 3.2. Формирование движений отдельным документом

В отдельных случаях движения формируются **другим документом**:
- Схожая обработка разных видов документов
- Групповая обработка
- Разделение функций исполнителей

**Пример:** `Платежное поручение` не делает движений → движения формирует `Списание с расчетного счета`

---

## 4. Правила для движений

### 4.1. Непроведённые и помеченные на удаление

⛔ Непроведённые и помеченные на удаление документы **не должны иметь активных движений**.

### 4.2. Проведение без движений

✅ Даже если документ не формирует движений, он **должен проводиться** — для логического отличия от «черновика».

---

## 5. Стабильность движений

### 5.1. Неизменность при повторном проведении

Если данные документа, влияющие на проведение, **не менялись** (например, изменён только `Комментарий`), повторное проведение **не должно изменять движения**.

**Исключение:** Движения формируются внешними алгоритмами (см. п.3.2).

### 5.2. Избегать зависимости от состояния регистров

⚠️ Результат формирования движений **не должен зависеть** от состояния учётных регистров (остатков), иначе результат будет зависеть от последовательности ввода документов.

**Исключение:** Алгоритмы, суть которых — анализ последовательности (партионный учёт).

---

## 6. Данные для формирования движений

### 6.1. Опора на данные документа

Документы при формировании движений должны **по максимуму опираться на собственные данные**.

### 6.2. Внешние данные (НСИ)

Если внешние данные (реквизиты НСИ) влияют на формирование движений:
- ✅ **Сохранять значения в документе**, либо
- ⛔ **Блокировать изменение** (механизм «Запрет редактирования реквизитов» БСП)

### 6.3. Настройки программы

Настройки (функциональные опции) должны оказывать **наименьшее влияние** на формирование движений.

**Приёмы:**
| Приём | Описание |
|-------|----------|
| Дата начала действия | Указывать период действия настройки |
| Значения по умолчанию | Заполнять отключённые обязательные поля значениями по умолчанию |
| Формирование без учёта настройки | Движения пишутся одинаково, отчёты скрывают измерение если отключено |

### 6.4. Если зависимость от настроек неизбежна

Предусмотреть одну из мер:
1. **Автоматическая обработка** в фоне после изменения настройки (предупреждать пользователя)
2. **Ручная обработка** пользователем (уведомлять о необходимости запуска)
3. **Предупреждение** о нежелательности изменения после начала учёта

---

## 7. Обновление логики движений

При изменении логики формирования движений необходимо:
- Предусмотреть **обработчики обновления ИБ**, либо
- Поддерживать **старые алгоритмы** для существующих документов

---

## 8. Отмена проведения

Для большинства событий отражение в учёте может быть **обратимым**.

✅ Использовать механизм **отмены проведения** документов.
