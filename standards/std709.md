# #std709 Технология разветвленной разработки конфигураций

> Область применения: управляемое приложение, мобильное приложение, обычное приложение.
> *Методическая рекомендация (полезный совет)*

---

## 1. Определения

| Термин | Описание |
|--------|----------|
| **Плановая версия** | Версия с существенным развитием функционала, срок выпуска назначается заранее |
| **Исправительная версия** | Срочная публикация исправлений критичных ошибок (редко — новый функционал) |
| **Технический проект** | Задание на доработку с чёткой целью и конечным списком изменений |
| **СППР** | Система проектирования прикладных решений — для ведения проектов и ошибок |

---

## 2. Разработка исправительных версий

### 2.1. Создание хранилища

Для каждой исправительной версии создаётся **новое хранилище** на основе конфигурации последней выпущенной версии.

⚠️ **Важно:** Создавать новое хранилище, **не копировать** основное!

### 2.2. Ограничения

- Не должно быть объёмных доработок (иначе — пересмотр сроков плановой версии)
- Все закладки должны содержать комментарий

### 2.3. Синхронизация

Все изменения исправительного релиза **должны синхронно повторяться** в основном хранилище.

При добавлении новых объектов — переносить **только через сравнение/объединение** (для сохранения внутренних идентификаторов).

### 2.4. Метки

При сборке — устанавливать метку с номером сборки на версии хранилища.

---

## 3. Разработка плановой версии

### 3.1. Основное хранилище

Разработка плановых версий ведётся в **основном хранилище**.

### 3.2. Требования к закладкам

Каждая закладка должна переводить конфигурацию из одного **рабочего состояния** в другое.

⛔ **Не допускается** закладка не полностью отлаженного функционала!

Основное хранилище **всегда** должно быть готово к выпуску.

### 3.3. Разрешённые работы в основном хранилище

| Работа | Условие |
|--------|---------|
| Исправление ошибок | Без перепроектирования и объёмного кодирования |
| Встраивание библиотек | Новые версии библиотек |
| Встраивание проектов | Только полностью отлаженные, прошедшие тестирование |
| Рефакторинг | В исключительных случаях |

### 3.4. Комментарии к закладкам

| Тип работы | Содержание комментария |
|------------|------------------------|
| Исправление ошибки | Номер + краткое наименование ошибки |
| Встраивание библиотеки | Название + точный номер версии |
| Встраивание проекта | Номер проекта + краткое наименование |
| Работа по проекту | Номер + наименование + описание изменений |

### 3.5. Правило одной закладки

Все изменения по техническому проекту переносятся **за одну закладку**. Если нужно несколько переносов — открывать несколько проектов.

---

## 4. Разработка технических проектов

### 4.1. Отдельное хранилище

Каждый технический проект ведётся в **отдельном хранилище**.

### 4.2. Настройка поддержки

При постановке на поддержку платформа устанавливает «Объект поставщика, не редактируется».

**Правило:** Менять на «Объект поставщика редактируется с сохранением поддержки» **только для изменяемых объектов** — максимально точечно.

Для изменения правил — захватывать только корень конфигурации.

### 4.3. Периодическое обновление

Ответственный периодически обновляет хранилище проекта до состояния основного.

**Факторы частоты:**
- Затрагивает ли проект объекты других ответственных
- Проводится ли рефакторинг общих механизмов
- Ведётся ли массовое исправление ошибок

### 4.4. Согласование сроков

После разработки — согласовать сроки тестирования и внесения в основное хранилище.

Крупные проекты — вносить **ближе к концу разработки**.

### 4.5. Внесение после тестирования

Внесение в основное хранилище — **после завершения отладочного тестирования**.

### 4.6. Итеративное обновление

Перед переносом — обновить хранилище проекта до состояния основного (итеративно, пока отличия не сведутся к изменениям проекта).

После каждой итерации — быстрая проверка работоспособности.

### 4.7. Проверка конфигурации

**Обязательно** перед закладкой запустить проверку конфигурации с максимальными настройками.

Закладка — только после исправления всех ошибок проверки.

### 4.8. Удаление хранилища

После переноса — удалить хранилище проекта.

## 5. Нумерация сборок

### 5.1. Когда увеличивать номер сборки

| Ситуация | Действие |
|----------|----------|
| Перед сборкой релиза | Увеличить номер |
| При закладке обработчика обновления ИБ | Увеличить номер |

### 5.2. Обработчики обновления

- Обработчик и изменение номера — **в одной закладке**
- Обработчик «привязан» к номеру сборки в этой закладке

### 5.3. Где изменять номер

1. В свойствах конфигурации
2. В процедуре `ОбновлениеИнформационнойБазы<ИмяБиблиотеки>.ПриДобавленииПодсистемы` (для БСП)

---

## Приложение 1. Создание хранилища проекта

1. Обновить базу из основного хранилища
2. Создать файл поставки (*.cf)
3. **Загрузить** конфигурацию из файла поставки в базу проекта
4. Создать хранилище (включится возможность изменения)
5. Добавить пользователя `ТолькоПросмотр` (без пароля, без захвата)
6. Добавить пользователей проекта (логин = фамилия, с правом захвата)

---

## Приложение 2. Обновление хранилища проекта

1. Обновить базу основного хранилища (ОХ)
2. Создать файл поставки ОХ
3. Захватить все объекты в хранилище проекта (ХТП)
4. Сохранить отчёт сравнения основной конфигурации и поставщика
5. Обновить конфигурацию из файла поставки
6. В окне объединения — включить «Показывать только дважды изменённые»
7. Для новых объектов поставщика — «Объект не редактируется»
8. Исправить затёртые изменения проекта
9. Сохранить новый отчёт сравнения
10. Сравнить файлы — отличий быть не должно
