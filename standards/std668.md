# #std668 Разработка ролей в библиотеках

> Область применения: управляемое приложение, мобильное приложение, обычное приложение.

---

## 1. Общий подход к границам функциональности библиотеки

При проектировании ролей в библиотеках рекомендуется придерживаться общего подхода:

| Включается в библиотеку | Не включается в библиотеку |
|-------------------------|---------------------------|
| Объекты метаданных, которые в неизменном или переопределённом виде войдут в состав конфигураций-потребителей | Объекты, специфичные для конкретной конфигурации-потребителя |

Специфичные объекты создаются на этапе внедрения и настройки библиотеки в конфигурации.

---

## 2. Роли для работы с данными библиотеки

В большинстве случаев библиотека должна предоставлять **готовый набор ролей** для работы со своими данными (справочники, регистры и т.п.).

**Пример:** подсистема анкетирования включает роли для:
- Добавления и изменения шаблонов
- Работы с опросами
- Ответов на вопросы анкет
- Просмотра ответов на вопросы
- Администрирования (настройки) подсистемы

### Исключения

| Ситуация | Описание | Пример |
|----------|----------|--------|
| Подчинённый объект | Библиотечный объект всегда подчинён объекту-владельцу конфигурации | Присоединённые файлы к номенклатуре, проектам — доступ задаётся в ролях владельцев |
| Неполный объект | Объект предполагает существенное переопределение в прикладных решениях | Справочники **Организации**, **ФизическиеЛица** — минимальная базовая реализация |
| Только алгоритмы | Библиотека не содержит данных, а только алгоритмы | — |

---

## 3. RLS в библиотечных ролях

В ролях могут быть определены не только права к библиотечным объектам, но и логика ограничений доступа на уровне записей (RLS — Row-Level Security).

### Требования к поставляемому RLS

✅ Поставляемый RLS должен быть разработан так, чтобы в прикладных решениях он использовался **«как есть»** и его не приходилось менять (дорабатывать).

✅ При обновлении библиотеки библиотечные роли всегда переносятся в конфигурацию «как есть».

### Исключения

| Ситуация | Действие при внедрении |
|----------|------------------------|
| В прикладном решении не предусмотрено настройки RLS | Тексты RLS должны быть **удалены** из библиотечных ролей |
| Предусмотрены прикладные сущности для настройки доступа (проекты, грифы доступа) | В тексты RLS должна быть **добавлена** логика ограничения для этих сущностей, либо принято решение не поставлять роли к таким объектам |

---

## 4. Правила поставки ролей

При использовании в библиотеке правил поставки для всех библиотечных ролей следует задавать правило поставки **«Изменения разрешены»**.

**Причина:** технологические особенности платформы 1С:Предприятие — при добавлении/удалении метаданных в конфигурации происходит неявное изменение ролей.

---

## Сводка

| Аспект | Рекомендация |
|--------|--------------|
| Роли для данных библиотеки | Предоставлять готовый набор ролей |
| Подчинённые объекты | Роли не создаются, доступ через владельца |
| Неполные объекты | «Полноценные» роли не предоставляются |
| RLS | Разрабатывать для использования «как есть» |
| Правило поставки | «Изменения разрешены» для всех ролей |
