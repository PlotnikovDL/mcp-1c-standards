# #std760 Ограничения на регламентные задания при работе в модели сервиса

> Область применения: управляемое приложение.

---

## 1. Запрет разделённых заданий

В прикладных решениях для работы в модели сервиса по [Технологии 1cFresh](https://v8.1c.ru/platforma/tekhnologiya-1cfresh/) **не должно быть** регламентных заданий, включённых в состав любого из разделителей.

### 1.1. Причина

При большом количестве областей данных в одной ИБ разделённые регламентные задания могут:
- Вызвать **перегрузку** рабочих процессов
- Серьёзно **затруднить работу** пользователей сервиса

---

## 2. Подсистема «Очередь заданий»

Для регулярного выполнения кода в разделённой ИБ используйте подсистему БТС **Очередь заданий** или аналогичный механизм.

### 2.1. Пример 1: Единое расписание для всей ИБ

**Задача:** Ежемесячный пересчёт итогов регистров накопления.

❌ **Неправильно:**
- Включить задание в состав разделяющих общих реквизитов

✅ **Правильно:**
- Исключить задание из состава разделяющих общих реквизитов
- В модуле `ОчередьЗаданийПереопределяемый` добавить в процедуру `ПриПолученииСпискаШаблонов`:

```1c
Шаблоны.Добавить(Метаданные.РегламентныеЗадания.ПересчетИтогов.ИмяМетода);
```

### 2.2. Пример 2: Индивидуальное расписание для каждой области

**Задача:** Обмен с сайтом при включённой ФО, индивидуальное расписание.

❌ **Неправильно:**
- Предопределённое задание, включённое в разделители

✅ **Правильно:**
- **Непредопределённое** задание, исключённое из разделителей
- В `ОчередьЗаданийПереопределяемый.ПриОпределенииПсевдонимовОбработчиков`:

```1c
СоответствиеИменПсевдонимам.Вставить(Метаданные.РегламентныеЗадания.ОбменССайтом.ИмяМетода);
```

- При **включении** ФО:

| Ситуация | Процедура |
|----------|-----------|
| Задание не существует | `РегламентныеЗаданияСервер.ДобавитьЗадание` |
| Задание существует, выключено | `РегламентныеЗаданияСервер.ИзменитьЗадание` |

- При **выключении** ФО:

| Ситуация | Процедура |
|----------|-----------|
| Задание существует | `РегламентныеЗаданияСервер.УдалитьЗадание` |
| Задание существует, включено | `РегламентныеЗаданияСервер.ИзменитьЗадание` |

### 2.3. Пример 3: Выполнение от имени пользователя

❌ **Неправильно:**
- Разделённое задание + установка имени пользователя через менеджер

✅ **Правильно:**
- Задание, исключённое из разделителей
- Создание через `РегламентныеЗаданияСервер.ДобавитьЗадание` с передачей имени пользователя в параметрах

## 3. Управление заданиями через БСП

⛔ **Недопустимо** управлять регламентными заданиями напрямую через платформенный API.

❌ **Неправильно:**

```1c
// Ищем задание по наименованию.
Отбор = Новый Структура();
Отбор.Вставить("Метаданные", "ПроверкаЦен");
Задания = РегламентныеЗадания.ПолучитьРегламентныеЗадания(Отбор);

// Проверяем, что задание найдено.
Если Задания.Количество() <> 1 Тогда
    // Запись в журнал ошибки опущена.
    Возврат;
КонецЕсли;

// Включаем найденное задание.
НашеЗадание = Задания[0];
НашеЗадание.Использование = Истина;
НашеЗадание.Записать();
```

✅ **Правильно:**

```1c
// Ищем задание по наименованию.
Отбор = Новый Структура();
Отбор.Вставить("Метаданные", "ПроверкаЦен");
Задания = РегламентныеЗаданияСервер.НайтиЗадания(Отбор);

// Проверяем, что задание найдено.
Если Задания.Количество() <> 1 Тогда
    // Запись в журнал ошибки опущена.
    Возврат;
КонецЕсли;

// Включаем найденное задание.
НашеЗадание = Задания[0];
Параметры = Новый Структура();
Параметры.Вставить("Использование", Истина);
РегламентныеЗаданияСервер.ИзменитьЗадание(НашеЗадание.УникальныйИдентификатор, Параметры);
```

## 4. Ограничения точности расписания

Подсистема **Очередь заданий** не гарантирует выполнение в точном соответствии с расписанием.

### 4.1. От чего зависит точность

| Фактор | Влияние |
|--------|---------|
| Общее количество запланированных заданий | ↑ заданий → ↓ точность |
| Длительность выполнения заданий | ↑ длительность → ↓ точность |
| Количество исполняющих потоков | ↑ потоков → ↑ точность |

⚙️ Регулируется константой **«Максимальное количество исполняющихся фоновых заданий»**.

### 4.2. Рекомендация

✅ **Не предоставлять** пользователям возможность настройки расписания в режиме сервиса.

---

## 5. Оперативная реакция системы

Если очередь заданий не обеспечивает требуемую оперативность:

### 5.1. Push-уведомления

Если есть техническая возможность получать push-уведомления от внешней системы:
- **Не использовать** регламентное задание
- Загружать данные **только при получении уведомления**
- Отправлять данные **только при наличии потребности**

**Пример:** Система взаимодействий — приём входящего SIP-звонка.

### 5.2. Клиентские обработчики

Если push недоступен:
- Оставить регламентное задание (через очередь)
- Организовать оперативную работу **при фактической работе пользователя** в соответствующем рабочем месте

### 5.3. Пример: Работа с почтой

**Проблема:** Задание должно выполняться раз в 5 минут, но в нагруженной базе запускается раз в 1 ч 40 мин.

**Решение:**
1. Регламентное задание работает с доступной периодичностью
2. При **открытии списка писем** — разовая дозагрузка/отправка для учётных записей пользователя
3. **Клиентский обработчик ожидания** — регулярная отправка/получение с нужной периодичностью

⚠️ Серверный вызов выполнять в [длительной операции](https://its.1c.ru/db/v8std/content/642/hdoc), чтобы не вызывать задержек.

## 6. Сводная таблица

| Сценарий | Решение |
|----------|---------|
| Единое расписание для всех областей | `ОчередьЗаданийПереопределяемый.ПриПолученииСпискаШаблонов` |
| Индивидуальное расписание | `ОчередьЗаданийПереопределяемый.ПриОпределенииПсевдонимовОбработчиков` + `РегламентныеЗаданияСервер` |
| Управление заданиями | Только через `РегламентныеЗаданияСервер` |
| Оперативная реакция | Push-уведомления или клиентские обработчики |
