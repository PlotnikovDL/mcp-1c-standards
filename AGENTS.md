# Правила разработки mcp-1c-standards

## Назначение

- Этот репозиторий содержит Python MCP-сервер `mcp-1c-standards` для поиска по стандартам разработки 1С.
- Источник стандартов остается внешним: `C:\projects\1c-tools\1c-docs\standards`.
- Не копировать стандарты, веса моделей, embeddings-кэш и виртуальное окружение в этот репозиторий.

## Рабочий режим

- Перед изменением файлов кратко описывать, что будет изменено и зачем, затем ждать явного подтверждения пользователя.
- Изменения делать маленькими шагами.
- Не менять модель, формат кэша, chunking, scoring или публичные MCP tools без отдельного согласования.
- Не коммитить изменения, не менять ветки и не выполнять операции Git с историей без прямой просьбы пользователя.

## Архитектурные границы

- Сервер отвечает только за стандарты 1С: `search_standards`, `read_standard`, `list_standards`.
- Не добавлять сюда интеграцию с `mcp-1c-ai`, BSL Language Server, EDT или синтакс-помощником.
- Автообучение, feedback-базы и пользовательская аналитика не входят в этот MCP.
- Кэш `.cache` является техническим и должен пересоздаваться из markdown-стандартов.

## Проверка

- Для изменений тестов и документации запускать из корня проверяемой рабочей копии только согласованный изолированный набор:
  ```powershell
  & "C:\projects\1c-tools\mcp-1c-standards\.venv\Scripts\python.exe" -I -S -B .\tests\run_isolated.py
  ```
  Используется установленный NumPy без изменения окружения. `.pth` и `sitecustomize` не выполняются; модели, сеть и запуск дочерних процессов запрещены защитой тестового процесса. Документы и кэш — только синтетические во временном каталоге.
- Набор выполняет индекс с подставными моделями и проверяет контракт сервера статически через AST. Он не импортирует модуль сервера или общий runtime, не запускает MCP/WMI и не подтверждает реальный обмен `initialize` / `tools/list`.
- После изменения рабочего Python-кода дополнительно согласовать и выполнить проверку импортов индекса и сервера в изолированной среде. Обычный импорт сервера выполняет регистрацию MCP, создание прокси и проверку аргумента `--shared-worker`; это не чистая синтаксическая проверка. Не выполнять его с произвольными аргументами и рабочими каталогами корпуса/кэша/runtime.
- После изменения зависимостей выполнять `python -m pip check` в согласованном изолированном окружении. Не устанавливать пакеты и не менять рабочее окружение как побочный эффект проверки.
- Если менялась логика поиска, отдельно согласовать smoke test через MCP `mcp-1c-standards` для `search_standards`, `read_standard`, `list_standards`. Внутреннее имя общего worker `1c-standards` не является именем подключения Harness и не переименовывается автоматически.
- Реальные модели, загрузки весов, пересборку рабочего кэша, WMI/HTTP-workers и подключение редакторов проверять отдельными согласованными этапами. Режим `fast` не является безмодельным.
- Ожидаемые ошибки (`expectedFailure`) фиксируют неисправленные дефекты. Код 2 изолированного набора означает такие дефекты или пропуски покрытия, а не полную успешность. Не разрешать pickle для обхода ошибки чтения NumPy-кэша. После согласованного исправления пересмотреть соответствующую отметку ожидаемого сбоя.
- В финальном ответе отдельно указывать успешные проверки, воспроизведённые дефекты, пропуски и невыполненные интеграционные этапы.
