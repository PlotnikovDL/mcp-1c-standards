# #std689 Настройка ролей и прав доступа

> Область применения: управляемое приложение, обычное приложение.

> Действует для конфигураций УП (ERP), УТ 11 и входящих в них библиотек.
> Для других конфигураций рекомендуется к использованию.
> Содержит уточнения к требованиям других стандартов.

---

## 1. Общие положения

### 1.1. Атомарные роли

Роли создаются **«атомарными»** — дающими права на доступ к элементарным функциям программы. Из этих элементарных ролей создаются профили пользователей, которые назначаются пользователям средствами БСП.

**Цель:** на типовом внедрении не должно возникать необходимости в создании новых ролей.

**Исключение:** для ролей внешних пользователей задаётся исчерпывающий набор прав к необходимым объектам (например, `ПартнерСамообслуживание`).

### 1.2. Роли ПолныеПрава и АдминистраторСистемы

Роль **ПолныеПрава** (`FullAccess`) совместно с ролью **АдминистраторСистемы** (`SystemAdministrator`) даёт неограниченный доступ (без RLS) ко всем объектам.

### 1.3. Запрет интерактивного удаления

❌ Ни одна роль (включая `ПолныеПрава` и `АдминистраторСистемы`) **не должна** давать право на интерактивное удаление ссылочных объектов.

- После создания нового объекта — зайти в роль `ПолныеПрава` и отключить право интерактивного удаления.

### 1.4. Право на удаление

Только роли `ПолныеПрава` и `АдминистраторСистемы` должны давать право на удаление ссылочных объектов.

### 1.5. Права для новых объектов

Только для роли `ПолныеПрава` должен быть установлен флаг **«Устанавливать права для новых объектов»**. Для всех остальных ролей — снят.

### 1.6. Права только для администратора

Если право может быть использовано только администратором — достаточно, чтобы это предоставлялось ролями `ПолныеПрава` или `АдминистраторСистемы`. Создавать отдельные роли не требуется.

### 1.7. Привилегированный режим при проведении

Во всех документах, предполагающих проведение, должны быть выставлены флаги:
- «Привилегированный режим при проведении»
- «Привилегированный режим при отмене проведения»

**Следствие:** не нужно создавать роли, дающие права на изменение регистров, подчинённых регистраторам.

**Исключение:** документы для непосредственной корректировки записей регистров могут проводиться с проверкой прав доступа — тогда необходимо предусмотреть роли на изменение регистров.

### 1.8. Функциональные опции

Во всех функциональных опциях должны быть выставлены флаги **«Привилегированный режим при получении»**.

**Исключение:** параметризированные ФО, для которых разработчик специально предусматривает различия в получаемых значениях пользователями с разными правами.

### 1.9. Общие права

Не должно быть ролей, кроме стандартных ролей БСП, которые дают общие права (`Администрирование`, `ТонкийКлиент` и т.п.).

- При создании новой роли — следить, чтобы эти права были выключены.

### 1.10. Базовые права

Для неконфиденциальных данных и общедоступных функций не требуется создавать отдельную роль на чтение — следует включать эти права в роли:
- **БазовыеПрава\<ИмяБиблиотеки\>** (`BasicAccess<LibraryName>`)
- **БазовыеПраваВнешнихПользователей\<ИмяБиблиотеки\>** (`BasicAccessExternalUser<LibraryName>`)

Примеры: константы, общенациональные классификаторы, общие формы выбора периода.

### 1.11. Роли и подсистемы

Не допускается, чтобы одна роль давала права на объекты, которые относятся к разным подсистемам.

## 2. Правила создания ролей к элементарным функциям

### 2.1. Объединение объектов в функции

Объекты необходимо объединить в **элементарные функции**. Если объекты входят в одну функцию — не может быть задачи, когда доступ к этим объектам может быть разным.

**Пример объединения:**
Документ «Заказ клиента» и регистр накопления «Заказы клиентов» (хранит остатки неотгруженных товаров) — можно объединить в одну функцию, т.к. регистр является отражением состояния табличной части заказа.

**Пример разделения:**
Документ «Реализация товаров и услуг» и регистр «Товары к отгрузке» — разные функции, т.к. кладовщик может иметь права на регистр, но не на документ.

### 2.2. При сомнениях — разделять

Если есть сомнения, могут ли два объекта быть отнесены к одной функции — лучше выделить их в разные.

### 2.3. Один объект — одна функция

Каждый объект должен быть отнесён к элементарной функции, и **только к одной**.

### 2.4. Разные библиотеки — разные функции

Объекты, относящиеся к разным библиотекам, не могут быть отнесены к одной элементарной функции.

---

## 3. Ссылочные объекты и регистры

### 3.1. Роли для функций

Для функций, включающих ссылочные объекты и независимые регистры сведений, создаётся **две роли**:

| Роль | Англ. название |
|------|----------------|
| **Чтение\<ИмяФункции\>** | `Read<FeatureName>` |
| **ДобавлениеИзменение\<ИмяФункции\>** | `AddEdit<FeatureName>` |

Или **Изменение\<ИмяФункции\>** (`Edit<FeatureName>`), если добавление выполняется автоматически или только администратором.

### Права в ролях

**Чтение\<ИмяФункции\>:**
- Чтение, Просмотр, Ввод по строке

**Изменение\<ИмяФункции\>** (включает права роли Чтение, а также):
- Изменение, Редактирование
- Проведение, Отмена проведения, Интерактивное проведение, Интерактивная отмена проведения, Интерактивное изменение проведённых (для документов)
- Управление итогами (для регистров)

**ДобавлениеИзменение\<ИмяФункции\>** (включает права роли Изменение, а также):
- Добавление, Интерактивное добавление
- Интерактивная пометка удаления, Интерактивное снятие пометки удаления

### 3.2. Регистры, подчинённые регистратору

Обычно не требуется назначать права на изменение (см. п. 1.7).

---

## 4. Журналы документов

### 4.1. Журнал в одной функции

Если все документы журнала отнесены к одной элементарной функции — права на чтение и просмотр журнала нужно включить во все роли этой функции.

### 4.2. Особенность платформы

Если у пользователя нет прав на чтение любого документа, входящего в журнал — платформа не даёт доступ ко всем графам журнала для всех документов.

**Следствие:** нет смысла создавать отдельную роль для журнала.

---

## 5. Константы

### 5.1. Константы только для администратора

Права на изменение и редактирование — только у `ПолныеПрава` или `АдминистраторСистемы`. Эти роли должны включать также права на чтение и просмотр.

### 5.2. Константы для пользователей

Включить права в уже имеющуюся «настроечную» роль или создать роль **Изменение\<ИмяКонстанты\>** (`Edit<ConstantName>`).

### 5.3. Неконфиденциальные константы

В подавляющем большинстве случаев права на чтение и просмотр нужно назначать ролям `БазовыеПрава<ИмяБиблиотеки>` и `БазовыеПраваВнешнихПользователей<ИмяБиблиотеки>`.

**Преимущество:** избежать неоправданной установки привилегированного режима при чтении из кода.

### 5.4. Конфиденциальные константы

Создать роль **Чтение\<ИмяКонстанты\>** (`Read<ConstantName>`). Если доступно только администратору — отдельную роль создавать не требуется.

---

## 6. Подсистемы в главном командном интерфейсе

### 6.1. Роль для подсистемы

Для каждой подсистемы верхнего уровня создать роль **Подсистема\<ИмяПодсистемы\>** (`Subsystem<SubsystemName>`), дающую право на просмотр.

### 6.2. Форма настроек

Если часть настроек и справочников отображается в отдельной форме (например, «Настройки и справочники») — роль подсистемы должна включать права на просмотр этой формы.

---

## 7. Отчёты

### 7.1. Отчёт на основе одной функции

Права на отчёт можно включить в роли, созданные по этой функции.

**Пример:** отчёт по исполнению заказов клиентов строится на основе регистра «ЗаказыКлиентов» — права включить в роль чтения регистра.

### 7.2. Отдельная настройка прав к отчёту

Если на внедрении может возникнуть задача отдельной настройки — создать роль **ПросмотрОтчета\<ИмяОтчета\>** (`ViewReport<ReportName>`), дающую права использования и просмотра.

### 7.3. Отчёт на основе нескольких функций

Создать роль **ПросмотрОтчета\<ИмяОтчета\>**.

**Пример:** отчёт по выполнению плана продаж строится на данных о планах и о продажах — разные функции.

### 7.4. Объединение однотипных отчётов

Допускается при условиях:
- Отчёты не входят в другие элементарные функции
- На внедрении не может возникнуть задачи различной настройки прав

---

## 8. Обработки и общие формы

### 8.1. Обработки-рабочие места

Для обработки, представляющей рабочее место (есть отдельная команда в ГКИ), создать роль **ИспользованиеОбработки\<ИмяОбработки\>** (`UseDataProcessor<DataProcessorName>`), дающую права на просмотр и использование.

❌ Не допускается объединять права к разным обработкам-рабочим местам в одной роли.

### 8.2. Вспомогательные обработки

Права к вспомогательным обработкам (подбор товаров, формирование печатных форм) назначать роли `БазовыеПрава<ИмяБиблиотеки>`.

### 8.3. Обработки для администратора

Права назначать только роли `ПолныеПрава` (или `АдминистраторСистемы`), не создавая отдельных ролей.

### 8.4. Общие формы

Правила применяются аналогично. Роль: **ИспользованиеОбщейФормы\<ИмяОбщейФормы\>** (`UseCommonForm<CommonFormName>`).

---

## 9. Команды

### 9.1. Команды без изменения данных

Право на просмотр назначать роли, которая даёт право на просмотр объекта.

- Проставлять права и в роли чтения, и в роли изменения
- Права на команды печати из обработок — назначать роли `БазовыеПрава<ИмяБиблиотеки>`

### 9.2. Команды с изменением данных

Право на просмотр назначать роли, которая даёт права на изменение объектов.

---

## 10. Права, не связанные с доступом к объектам

### 10.1. Наименование роли

Создавать роль **\<НаименованиеПрава\>**, не дающую доступ ни к одному объекту. В наименовании **не использовать** слово «Право».

| ✅ Правильно | ❌ Неправильно |
|-------------|---------------|
| `ОтклонениеОтУсловийЗакупок` | `ПравоСозданияВыпускПродукцииБезЗаказа` |

### 10.2. Проверка в коде

Проверять наличие роли у пользователя. Пользователь с ролью `ПолныеПрава` должен проходить проверку без необходимости включения этой роли в профиль.

**Использовать:** `Пользователи.РолиДоступны()`

### 10.3. Только проверка ролей

Использование других механизмов, кроме проверки наличия роли, при реализации дополнительных прав пользователя **не допускается**.

---

## 11. Права для внешних пользователей

Роли для внешних пользователей (представленных справочниками `Сотрудники`, `Партнеры`, `Физические лица` и др.) называть с определённым **префиксом**.

**Пример с префиксом «Самообслуживание»:**

| Имя роли | Синоним |
|----------|---------|
| `СамообслуживаниеОформлениеПретензий` | Самообслуживание: оформление претензий |
| `СамообслуживаниеПросмотрОтчетаСостояниеВыполненияЗаказа` | Самообслуживание: просмотр отчёта «Состояние выполнения заказа» |
| `СамообслуживаниеДобавлениеИзменениеКонтрагентов` | Самообслуживание: добавление и изменение контрагентов |

---

## 12. Права к устаревшим объектам

Устаревшие объекты с префиксом **Удалить** должны быть исключены из всех ролей, кроме `ПолныеПрава` или `АдминистраторСистемы`.

---

## Сводка по наименованиям ролей

| Назначение | Имя роли | Англ. |
|------------|----------|-------|
| Чтение функции | Чтение\<Функция\> | Read\<Feature\> |
| Изменение функции | Изменение\<Функция\> | Edit\<Feature\> |
| Добавление и изменение | ДобавлениеИзменение\<Функция\> | AddEdit\<Feature\> |
| Просмотр отчёта | ПросмотрОтчета\<Отчёт\> | ViewReport\<Report\> |
| Обработка-рабочее место | ИспользованиеОбработки\<Обработка\> | UseDataProcessor\<DataProcessor\> |
| Общая форма | ИспользованиеОбщейФормы\<Форма\> | UseCommonForm\<Form\> |
| Подсистема | Подсистема\<Подсистема\> | Subsystem\<Subsystem\> |
| Изменение константы | Изменение\<Константа\> | Edit\<Constant\> |
| Чтение константы | Чтение\<Константа\> | Read\<Constant\> |
